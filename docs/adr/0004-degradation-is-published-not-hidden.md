# Degradation is published, not hidden

The provider layer already knows when a number came from a fallback source or from a stale on-disk cache — `ProviderRegistry.call()` returns a `meta` block with `used_fallback`, `from_cache`, and `degraded`. Every collector currently throws that block away (`quote = quote_out["result"]`), so a payload assembled entirely from yesterday's cached JSON is stamped `freshness_status: "fresh"`, `quality: 1.0`, and shipped with the same visual weight as a live quote. The dashboard has no way to lie *less* than this: it is structurally incapable of telling the truth about its own inputs.

We considered three options. **Fail closed** (refuse to publish a degraded payload) protects the reader but turns any upstream hiccup into a blank site, which is worse for a dashboard whose whole job is "what is the market doing right now". **Publish silently** is the status quo and is disqualified. We chose **publish honestly and penalize**: degraded data ships, but it ships *labelled and discounted*.

Concretely, this fixes three things as one decision:

- **`meta` propagates.** Collectors thread the provider `meta` into the envelope instead of discarding it. `source` becomes the provider actually used, not a hardcoded `["yfinance", "akshare"]` literal.
- **Degradation costs something.** `quality` is multiplied by the degrade factor when any input was a fallback or a cache read, and `freshness_status` resolves to `degraded` rather than `fresh`. A cache read past `degrade.cache_max_age_hours` is not a cache read at all — it is `missing`.

  Enforcing that cap is not a matter of switching on a check that was merely forgotten. `_save_last_good` writes `{"method", "data"}` and **no timestamp at all**, so there is nothing on disk to compare an age against. `cache_max_age_hours: 24` is dead config everywhere except `rss_news.py`, which reads it independently. Enforcement therefore requires a cache *format* change — entries gain a `fetched_at` — and a rule for the entries already on disk. An entry with no `fetched_at` is treated as beyond max age: undated means expired. The one-time cost is a cold cache on first deploy, which is the correct price for never again replaying a month-old quote as live.
- **`risk.json` stops self-certifying.** `RiskEnvelope` defaults `freshness_status` to `"fresh"`, which means a risk score computed from four stale inputs reports itself as live. It inherits `BaseEnvelope` instead, making freshness a required field derived from the inputs that actually fed it.

The trade-off is real: the site will visibly show more "degraded" states than it does today, and some of those states were previously invisible-and-fine. We are choosing a dashboard that occasionally admits it is guessing over one that is confidently wrong. This is hard to reverse because it changes the envelope contract, the freshness state machine, and every UI surface that renders a freshness badge.

## Consequences

- The six-state freshness model (`fresh` / `delayed` / `stale` / `empty` / `missing` / `degraded`) now has a real producer for `degraded`; `finalize_freshness` priority ordering (`missing` > `degraded` > `empty` > time-based) is load-bearing rather than theoretical.
- `degraded_domains` gains its first reader. It was populated and never consumed.
- UI must distinguish *live*, *degraded*, and *cached* rather than the current binary fresh/not-fresh — `fresh-*` tokens (ADR 0002) already carry enough vocabulary; only `degraded` needs a distinct affordance from `stale`.
- Single-provider domains still degrade. `ProviderRegistry.call()` reaches the last-good cache branch whenever *all* providers fail, and that branch sets `degraded: True` and `from_cache: True` regardless of how many providers the domain had. So `crypto`, `macro`, `a_share` and `news` — each with one enabled provider — degrade through the cache exactly like `quotes` does. What they cannot do is `used_fallback` to a *second live provider*; only `quotes` and `calendar` have a real fallback chain. Tests must cover the cache-degrade path for single-provider domains specifically, because that is where the only degradation they can express lives. (`binance_public` remains `enabled: false`; re-enabling it is out of scope.)
- Snapshot fixtures that assert `freshness_status == "fresh"` on cache-backed data will fail. Those failures are the point.
- **The degrade factor is not currently a shared constant.** `0.8` is read from config in exactly one place (`providers/base.py:145`) and hardcoded in five others — `risk/confidence.py:37`, `collectors/macro.py:152`, `collectors/news.py:147`, `collectors/calendar.py:54`, `collectors/market.py:179`. Introducing the proxy discount against this codebase would add a seventh copy. Extracting the single constant is therefore a prefactoring step that must land *before* the proxy work, not after: make the change easy, then make the easy change.
- **Discounts compound.** The existing code already multiplies (`degrade_factor ** failed_count` in the collectors; `per_degrade` in `confidence.py`). The proxy discount follows the same precedent rather than inventing a second convention: a proxied indicator sourced from a degraded provider scores `degrade.data_quality_degrade_factor × confidence.proxy_discount_factor` — two distinct named knobs (`0.8 × 0.8 = 0.64` at the release defaults). They are deliberately independent: the degrade factor answers "how much does data_quality drop per failed input", the proxy discount answers "how much less do we trust an estimate than a measurement" (board ruling on #69). The pipeline run report names which discounts applied, so a 0.64 is never mistaken for an unexplained 0.8.
